# 03. 核心模型與業務流程

[← 回到架構總覽](00-架構總覽.md)

業務規則位於 [`internal/core/core.go`](../../internal/core/core.go)。`Service` 接受 context 和明確的輸入／模型，負責驗證、權限、密碼處理及使用案例協調；它不依賴 HTTP request 或 SQL query。

## 模型和 Store 介面

主要資料模型為 `User`、`Account`、`Event`、`Registration`，另有分別供會員與管理員列表使用的 `MyRegistration`、`EventRegistration`。`Account` 在 `User` 上增加 `PasswordHash`，但 `User` 沒有密碼 hash 欄位，因此 API 回應序列化使用 `User` 時不會輸出 hash。

`core.Store` 列出使用案例所需的 persistence 能力，PostgreSQL 在 [`internal/store/postgres.go`](../../internal/store/postgres.go) 實作它。這是依賴反轉的窄介面：core 描述要做什麼，adapter 決定如何用 SQL 做。

## 註冊、登入和 session

`RegisterUser` 會 trim 名稱、正規化 email 為小寫，檢查名稱長度、email 格式與 bcrypt 支援的密碼 byte 長度，再使用 bcrypt 雜湊後交給 Store。密碼要求 12 到 72 bytes；這裡檢查的是 bytes，不是 Unicode 字元數。

`Login` 查詢帳號並比較 bcrypt hash。登入成功後產生 32 bytes 的 crypto/rand 隨機值，以 URL-safe base64 回傳；資料庫只存 `TokenHash` 的 SHA-256 結果，session 有效期是 24 小時。`Authenticate` 對收到的 token 再算 hash 查詢有效 session；`Logout` 撤銷該 hash 對應的 session。

## 活動與權限

`CreateEvent` 要求 actor role 為 `admin`，並檢查標題、描述、容量和開始時間。`UpdateEvent` 與 `CloseEvent` 也在 service 做 admin 檢查；Store 另外限制只能更新仍 open 且尚未開始的活動。管理員查看名單時由 `ListEventRegistrations` 檢查角色；會員自己的報名則按 actor 的 user ID 查詢。

授權規則在 core 再檢查一次很重要：即使未來 HTTP handler 或路由組態有誤，業務層仍不應讓 member 建立活動或讀取其他人的活動名單。

## 登入後流程的責任切分

```text
HTTP 層：解析 Bearer token、JSON 與 URL ID
core 層：檢查身份、角色、格式、範圍與開始時間規則
Store 層：確保資料庫狀態轉移、唯一性及名額一致性
```

`Register` 和 `CancelRegistration` 在 core 中刻意很薄，因為容量競爭必須由資料庫原子操作決定；先在 Go 中讀名額再寫入會有 race condition。

## Review 時追問

- `Login` 對不存在帳號和錯誤密碼是否有相同的外部錯誤？目前都回 `ErrUnauthorized`，但 bcrypt 工作量只會在帳號存在時執行，仍可能有時間差。
- email 正規化是否要涵蓋所有直接建立帳號的路徑？會員註冊與 admin CLI 都會轉成小寫。
- 取消報名是否允許在活動關閉或開始之後進行？目前 core 不限制，Store 也只要求存在未取消報名。
- 密碼 byte 限制、容量上限和分頁上限是否符合產品需求？變更時應同步修改 API 契約和測試。
- 是否需要把時鐘抽象化以便測試邊界時間？目前 Service 使用 `time.Now`，部分資料庫判斷也使用資料庫 `now()`。
